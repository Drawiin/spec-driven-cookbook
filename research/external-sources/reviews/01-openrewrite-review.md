## 1. Alignment Snapshot

Relevance to a spec-driven AI coding framework: **4/5**. OpenRewrite and the dossier solve different problems — OpenRewrite is a deterministic Java-rooted refactoring engine, the dossier surveys LLM-driven spec frameworks — but the engine architecture maps unusually well onto open questions in the dossier. Recipes as named, parameterized, validated, composable transformations; preconditions as cheap deterministic filters before expensive work; `ScanningRecipe` with a typed accumulator; execution cycles with a self-declared "may need another cycle" flag; per-file change provenance; and distribution as versioned packaged artifacts are all sharper formalizations of patterns the dossier already gestures at. The Lossless Semantic Tree (LST) and isomorphic-vs-non-isomorphic visitor distinction are genuinely new lenses for AI editing that the dossier does not consider. The lower-relevance bits are tool-specific (YAML grammar, Maven/Gradle plugins, Styles).

## 3. NEW Items — Incorporation Proposals

- **Item**: Lossless Semantic Tree (typed, format-preserving IR for AI edits).
  - **Why it matters for the dossier's audience**: Every framework surveyed has an LLM produce text and then verifies after the fact. An IR-based substrate (typed nodes, preserved whitespace, tree-resident style) gives the model accurate type context for grounding and guarantees round-trip formatting — a structural answer to "code that runs vs code that works" and to the hallucinated-API problem.
  - **Proposed home**: `topics/patterns-worth-stealing.md`, new pattern in Group C (Verification and Quality), and a brief reference in `SUMMARY.md` §4 if the pattern lands as HIGH transferability.
  - **Proposed text**: "An alternative to text-level editing is to have the model propose changes against a typed, format-preserving intermediate representation (Lossless Semantic Tree, [https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees](https://docs.openrewrite.org/concepts-and-explanations/lossless-semantic-trees)) and let the framework print the IR back to source. Type information travels with each node, so the model has grounding against fabricated APIs; whitespace and local style are tree-resident, so unrelated lines are never reformatted. Adoption cost is high (per-language IR), but the correctness ceiling is meaningfully higher than after-the-fact text verification."

- **Item**: Recipe primitive + declarative `recipeList` composition (Findings #3 and #4 combined).
  - **Why it matters for the dossier's audience**: The dossier's primitives are phases, plans, tasks, and stories — all coarse-grained. OpenRewrite's recipe is a fine-grained, parameterized, validated, composable unit ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)) that lets a high-level spec decompose into ordered, traceable, testable sub-operations. Crucially, `recipeList` ([https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference)) lets deterministic and LLM-powered skills be uniformly composed in YAML.
  - **Proposed home**: `topics/workflow-and-orchestration.md` §3 (Sub-Agent Dispatch Patterns) as a new "Pattern D: Authored composition of typed transformations", plus a new Pattern in `topics/patterns-worth-stealing.md` Group B.
  - **Proposed text**: "OpenRewrite formalizes a transformation as a Recipe: a named, parameterized, validated unit with two flavors — imperative (code) and declarative YAML that composes other recipes via `recipeList` ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes), [https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference)). Translated to a spec-driven AI framework: define a 'skill' contract such that deterministic skills (regex/AST refactors) and LLM skills expose the same options and validation surface, then let high-level specs be authored as a YAML DAG of skills. The composition surface is the unit of reuse; the planner does tool-selection over the DAG, not over chat prompts."

- **Item**: Preconditions as cheap deterministic file filters.
  - **Why it matters for the dossier's audience**: Dossier gates are about coverage and decisions, not scope. Preconditions ([https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference)) attach a lightweight search recipe to every transformation that decides which files are eligible; ineligible files are skipped without invoking the heavy recipe. For LLM workflows this is the difference between "the model reads the whole repo" and "the model only sees the slice that matched a glob/AST query/type predicate".
  - **Proposed home**: `topics/self-healing-and-verification.md` §2 plan-time gates (add a "Scope precondition gate" sub-section), and `topics/patterns-worth-stealing.md` Group C.
  - **Proposed text**: "Require every AI editing skill to ship with a deterministic precondition (glob, AST query, type predicate, or short search recipe). Preconditions, as defined in OpenRewrite ([https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference)), gate which files a skill may touch *before* the LLM is invoked. This slashes token cost, scopes blast radius, and keeps the model's attention on a verified subset rather than the whole repo."

- **Item**: Isomorphic vs non-isomorphic visitors (safe vs structural edit distinction).
  - **Why it matters for the dossier's audience**: TLC's RED→GREEN immutability and GSD's plan-checker treat all edits with the same review intensity. OpenRewrite distinguishes provably structure-preserving edits from edits that may swap node types ([https://docs.openrewrite.org/concepts-and-explanations/visitors](https://docs.openrewrite.org/concepts-and-explanations/visitors)). The transfer is a tiered review gate: rename/retype/reformat = light review, replace-function-with-class = full review.
  - **Proposed home**: `topics/self-healing-and-verification.md` §8 implications, and `topics/patterns-worth-stealing.md` Group C.
  - **Proposed text**: "Adopt OpenRewrite's distinction between isomorphic (provably structure-preserving) and non-isomorphic (allows node-type replacement) edits ([https://docs.openrewrite.org/concepts-and-explanations/visitors](https://docs.openrewrite.org/concepts-and-explanations/visitors)). Map it to AI edits: classify each skill's output as 'safe' (rename, retype, format, comment) or 'structural' (replace function, change interface, alter control flow). Apply different review gates per class — safe edits can auto-merge after gate checks; structural edits require explicit human or higher-tier-model approval."

- **Item**: Recipe descriptors (`@Option`, displayName, `estimatedEffortPerOccurrence`, tags).
  - **Why it matters for the dossier's audience**: A planner LLM doing tool-selection over an opaque skill catalog is a known weakness; GSD's `requires:` frontmatter handles dependencies but not capability description. OpenRewrite recipes self-document their parameters and expected effort saved ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes), [https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference)), letting the planner choose on metadata alone and letting humans prioritize by `estimatedEffortPerOccurrence`.
  - **Proposed home**: `topics/patterns-worth-stealing.md` Group D (Pattern 15 area), as a sibling pattern to "Install-Time Profile + Surface Toggle".
  - **Proposed text**: "Require every AI skill to publish a typed manifest including parameters, display name, description, tags, and an `estimatedEffortPerOccurrence` field — modeled on OpenRewrite's recipe descriptors ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)). The manifest is the input the planner LLM does tool-selection over (no prompt-time prose), and `estimatedEffortPerOccurrence` lets product owners prioritize a backlog of automated migrations the way OpenRewrite users already do."

## 4. EXTENDS Items — Augmentation Proposals

- **Item**: Markers (per-AST-node metadata bag) augments confidence tagging.
  - **Existing passage**: `topics/patterns-worth-stealing.md` Pattern 13 (Confidence Tagging on Inferred Data; Graphify's `EXTRACTED` / `INFERRED` / `AMBIGUOUS` on relations).
  - **Why it matters**: Graphify's tags live on graph relations. OpenRewrite's Markers ([https://docs.openrewrite.org/concepts-and-explanations/visitors](https://docs.openrewrite.org/concepts-and-explanations/visitors)) live on every AST node and survive transformations — confidence, rationale, and source-of-truth links can co-locate with the code rather than the analysis artifact.
  - **Proposed text** (append to Pattern 13's "What to adapt" paragraph): "OpenRewrite's Markers ([https://docs.openrewrite.org/concepts-and-explanations/visitors](https://docs.openrewrite.org/concepts-and-explanations/visitors)) extend this pattern from analysis artifacts to source IR: a `Markers` bag on every AST node lets agents annotate code with rationale, confidence, source-of-truth links, and review status as structurally co-located metadata that survives transformations and is invisible at runtime."

- **Item**: `ScanningRecipe` augments the existing research-then-plan flow.
  - **Existing passage**: `topics/self-healing-and-verification.md` §2 (plan-time gates: research gate, requirements coverage); `topics/workflow-and-orchestration.md` §1 (GSD's `gsd-phase-researcher` → `RESEARCH.md` → planner).
  - **Why it matters**: Existing research phases pass freeform markdown to the planner. OpenRewrite's `ScanningRecipe` ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)) is a typed accumulator handed structurally between scan and edit phases — a "survey before edit" contract that the edit phase can rely on without re-reading the repo.
  - **Proposed text** (add as new sub-section in `topics/self-healing-and-verification.md` §2): "OpenRewrite's `ScanningRecipe` formalizes the survey-then-edit pattern with a typed accumulator: scanners populate a structured object that the edit phase reads, never re-reading source files ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)). Translated to AI workflows, the scan pass produces a typed project memo (deps used, patterns found, files matching predicates), and the edit pass consumes only that memo — not the whole repo and not the freeform research markdown."

- **Item**: Execution cycles with `causesAnotherCycle` augments the convergence loop.
  - **Existing passage**: `topics/self-healing-and-verification.md` §3 (`/gsd-plan-review-convergence`, max 3 cycles, stall detection); `node_repair_budget: 2`; TLC's max-3 diagnostic loop.
  - **Why it matters**: Dossier convergence loops are external (one diagnose-into-PLAN cycle is a re-run of the whole pipeline). OpenRewrite re-runs the *recipe pipeline* until quiescence within one invocation, capped at 3, and individual recipes self-declare `causesAnotherCycle` when they expect to need another pass ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)). This avoids converting every multi-pass edit into a separate user-facing run.
  - **Proposed text** (append to §3 plan-convergence-loop paragraph): "OpenRewrite extends this idea inside a single invocation: the recipe pipeline re-runs until no recipe changes anything, capped at 3 cycles by default, with each recipe self-declaring `causesAnotherCycle` when it knows its output may unblock another recipe ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)). Adopting a per-skill 'may-need-another-cycle' flag lets agentic edits converge typecheck/format/test passes without bespoke control loops or fresh user-initiated runs."

- **Item**: `Result.recipesThatMadeChanges` augments the sub-agent output contract.
  - **Existing passage**: `topics/patterns-worth-stealing.md` Pattern 6 (sub-agent output: status/files/gate/deviations/issues); `topics/workflow-and-orchestration.md` §5 (`feat(NN-MM):` commits).
  - **Why it matters**: Existing provenance is per-commit. OpenRewrite records, for every changed file, exactly which recipes contributed ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)). For PR review and audit of AI-driven changes, per-hunk attribution to (skill ID, prompt hash, model version, spec ID) is materially more useful than per-commit attribution.
  - **Proposed text** (extend Pattern 6's output contract): "Add a per-hunk attribution layer modeled on OpenRewrite's `Result` with `recipesThatMadeChanges` ([https://docs.openrewrite.org/concepts-and-explanations/recipes](https://docs.openrewrite.org/concepts-and-explanations/recipes)): persist, alongside each diff hunk, the skill ID, prompt hash, model version, and originating spec/decision ID. Every line in a PR can then be traced back to a spec, which makes audit and selective rollback feasible without re-running the workflow."

- **Item**: Versioned packaged recipe distribution augments install-time profiles.
  - **Existing passage**: `topics/patterns-worth-stealing.md` Pattern 15 (Install-Time Profile + Runtime Surface Toggle, GSD's `--profile=core,audit`).
  - **Why it matters**: Pattern 15 covers what is installed and what is active locally. OpenRewrite goes further: recipes ship as versioned JAR artifacts (`META-INF/rewrite/*.yml`), and `rewrite-recipe-bom` coordinates a catalog of compatible versions across third-party recipe modules ([https://docs.openrewrite.org/reference/yaml-format-reference](https://docs.openrewrite.org/reference/yaml-format-reference), [https://docs.openrewrite.org/running-recipes/getting-started](https://docs.openrewrite.org/running-recipes/getting-started)) — a shared, semver'd ecosystem rather than per-team forks.
  - **Proposed text** (append to Pattern 15 "What to adapt"): "Treat AI specs and skills as versioned, packaged artifacts (npm/OCI/PyPI) with semver and a BOM-style coordinator — the model OpenRewrite uses to ship recipes as JARs scanned for `META-INF/rewrite/*.yml` and aligned via `rewrite-recipe-bom` ([https://docs.openrewrite.org/running-recipes/getting-started](https://docs.openrewrite.org/running-recipes/getting-started)). This unlocks a shared catalog where third-party skill modules can be pulled in, pinned, and discovered (`mvn rewrite:discover` analog) instead of being copy-pasted into every repo."

## 5. Contradictions

None identified. OpenRewrite operates in a different problem domain (deterministic, typed Java refactoring) than the LLM-driven frameworks in the dossier; the source's claims about its own engine do not contradict any dossier claim about GSD/TLC/Spec Kit/etc. The only friction is conceptual: OpenRewrite's "typed IR is the substrate" worldview implicitly challenges the dossier's text-level editing assumption — but that is a NEW alternative to flag, not a contradiction.

## 6. Items rejected (with rationale)

- **Styles (declarative formatting configs)** — derivative of having an LST; without an IR substrate there is no transfer surface.
- **Recipe immutability + visitor-local mutable state** — Java/visitor authoring discipline; not a portable architectural pattern at the framework level.
- **Maven/Gradle plugin shape (`mvn rewrite:run`, `gradle rewriteRun`)** — tool-specific; the underlying compound-init pattern is already covered by Pattern 1 in the dossier.
- **`mvn rewrite:discover`** — closely analogous to GSD's `/gsd-help` and TLC's trigger-phrase index; no new design content.
- **Moderne (commercial mass-refactoring layer)** — covered too lightly in the source to extract a transferable mechanism (the only specific claim, "build LSTs in pieces so they need not fit in memory", is implementation-level).
