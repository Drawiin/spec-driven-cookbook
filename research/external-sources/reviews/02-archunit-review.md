## 1. Alignment Snapshot (1-5 + one paragraph)

**4 / 5 — High alignment, two genuinely new mechanisms.**

ArchUnit is, in effect, the canonical implementation of the dossier's "test-as-spec" principle (Pattern 11) applied to architectural invariants rather than functional behavior, and it shares the dossier's general posture that verification should ride on the project's existing test runner with rule failures expressed as ordinary assertions. Most of its DSL surface (slices, JPMS-like modules, `GeneralCodingRules`) is Java-specific and out of scope. However, two mechanisms are load-bearing and genuinely absent from the dossier: (a) `FreezingArchRule` with a VCS-committed `ViolationStore` and auto-shrinking ratchet semantics — a clean answer to "how do you introduce a new constraint into a brownfield codebase without rewriting it first" — and (b) `adhereToPlantUmlDiagram(...)`, where a single PlantUML component diagram is *both* the human-readable architecture spec and the machine-checked rule set. Both deserve incorporation; the freeze-baseline pattern in particular fills a gap in the dossier's brownfield/decision-coverage story.

## 3. NEW Items — Incorporation Proposals

- **Item 2 — Frozen baseline with ratchet semantics** / **Why it matters:** the dossier currently has no answer for "introduce a new architectural or quality constraint into a brownfield codebase that already has thousands of pre-existing violations." Asymmetric Decision Coverage Gates (Pattern 10) cover individual decisions but do not scale to whole-violation-set baselining. / **Proposed home:** add as **Pattern 20: Frozen Baseline with Ratchet Semantics** in `topics/patterns-worth-stealing.md` Group C *Verification and Quality*, plus a paragraph in `topics/self-healing-and-verification.md` §8 *Implications*. / **Proposed text:**
  > **Pattern 20: Frozen Baseline with Ratchet Semantics.** *Origin: ArchUnit (`FreezingArchRule`, `ViolationStore`).* Problem: a new rule introduced into a grown codebase can produce thousands of violations, none of which the AI agent caused — uniform blocking is hostile, uniform warning lets new violations slip in. ArchUnit's `FreezingArchRule.freeze(rule)` snapshots every existing violation into a VCS-committed `ViolationStore` text file; CI fails only on *new* violations and the store auto-shrinks when violations are fixed. Two CI-side safety flags (`freeze.store.default.allowStoreCreation=false`, `allowStoreUpdate=false`) prevent silent baseline growth. Transferability: HIGH for any framework whose verifiers run against legacy code. Adapt: a "freeze on adoption" mode where new constraints snapshot the current violation set; the AI agent ships under the new rule today, with strict enforcement on its diff and ratchet-down semantics on the inherited debt. (Source: https://www.archunit.org/userguide/html/000_Index.html §8.6.)

- **Item 3 — `allowStoreCreation` / `allowStoreUpdate` baseline-mutation guards** / **Why it matters:** without these flags, a freeze baseline silently grows when CI runs in record mode; the ratchet-down property is lost. / **Proposed home:** sub-paragraph inside the Pattern 20 entry above (paired with Item 2). / **Proposed text:**
  > Two configuration flags govern who may *write* to the violation store: `freeze.store.default.allowStoreCreation` (gates first-time creation) and `allowStoreUpdate` (gates baseline modification). In CI both are set to `false` — CI may only *read* the baseline. Local developers may set them `true` to refreeze after intentionally accepting new debt. This separates "CI enforces the ratchet" from "humans may explicitly grow the baseline," and prevents a misconfigured pipeline from silently re-baselining failures away. (Source: https://www.archunit.org/userguide/html/000_Index.html §8.6.)

- **Item 4 — Diagram-as-Executable-Spec (PlantUML → ArchRule)** / **Why it matters:** the dossier covers governance prose (Constitution) and structured deltas (OpenSpec current-vs-proposed) but no mechanism where a *diagram itself* is the contract. AI agents are good at producing diagrams; making the diagram round-trip into rule enforcement closes a drift loop. / **Proposed home:** add as **Pattern 21: Diagram-as-Executable-Spec** in `topics/patterns-worth-stealing.md` Group D *Extensibility and Adaptability*, with cross-reference from Pattern 16 *Constitution*. / **Proposed text:**
  > **Pattern 21: Diagram-as-Executable-Spec.** *Origin: ArchUnit (`adhereToPlantUmlDiagram(url, consideringAllDependencies())`).* Problem: architecture diagrams drift silently from the code they purport to describe; an AI agent reading a diagram has no signal whether it still matches reality. ArchUnit lets a PlantUML component diagram with stereotyped components (`<<..pkg..>>`) be both the human-readable architecture and an executable `ArchRule`: components map to package identifiers, arrows are the only allowed dependencies, and any code-level edge not present in the diagram fails the build. Transferability: MEDIUM-HIGH — applicable wherever a structured diagram format (PlantUML, Mermaid component graphs, C4 model exports) can be parsed into a dependency contract. Adapt: pick one diagram format as canonical, give the AI agent a tool that derives rules from it, and run those rules on every commit. The diagram is the contract; the agent cannot drift without the diff failing. (Source: https://www.archunit.org/userguide/html/000_Index.html §8.5.)

- **Item 7 — Importable, parameterized rule libraries** / **Why it matters:** Pattern 15 governs the framework's own skill surface, but says nothing about how a project consumes *external* constraint packs (org-wide architecture standards, client-specific conventions, regulatory rule sets). ArchUnit's `ArchTests.in(...)` is the canonical mechanism. / **Proposed home:** new bullet in `topics/patterns-worth-stealing.md` Pattern 15 *adjacent* slot (or a sibling Pattern 15b), and a row in the cross-framework table in `topics/multi-runtime-support.md` if appropriate. / **Proposed text:**
  > **Companion to Pattern 15 — Importable Spec Packs.** ArchUnit's `ArchTests.in(SharedRules.class)` plus `@AnalyzeClasses(packages=...)` lets an organization publish a rule library (a JAR of `ArchRule` static fields) that downstream projects import like any other test dependency. Adapt: spec packs become installable dependencies on top of the framework. A project declares which packs are active (via `requires:` frontmatter or a `spec-packs.yaml`), and the AI agent treats them as hard constraints. Analog to ESLint shared configs or shared lint rule sets, but with semantic, cross-file architectural scope. (Source: https://www.archunit.org/userguide/html/000_Index.html §7.4, §9.)

- **Item 8 — Named Architectural Primitives Vocabulary** / **Why it matters:** the dossier's vocabulary is process-shaped (phases, gates, agents). A small named-primitive vocabulary for *architecture* (layered, onion, hexagonal, slices) gives the AI agent a high-signal target to comply with. / **Proposed home:** new paragraph in `topics/patterns-worth-stealing.md` (could be a Pattern 22 or fold into Pattern 21), and a sentence in `topics/self-healing-and-verification.md` §2 plan-time gates as a future direction. / **Proposed text:**
  > **Named Architectural Primitives.** ArchUnit's Library API encodes a handful of well-known architectures as parameterized DSL methods: `layeredArchitecture().layer(..).definedBy(..).whereLayer(..).mayOnlyBeAccessedByLayers(..)`, `onionArchitecture().domainModels(..).domainServices(..).applicationServices(..).adapter(..)`, `slices().matching(..).should().beFreeOfCycles()`. Adapt: ship a curated catalog of named architectural patterns as first-class spec primitives ("this project is layered: controller → service → persistence"; "this project is onion: domain ← application ← adapters"). The AI agent then writes against a small, well-known parameter-driven vocabulary instead of free-form architectural prose, which is much higher signal at a tiny token cost. (Source: https://www.archunit.org/userguide/html/000_Index.html §8.1, §8.2, §8.4.)

## 4. EXTENDS Items — Augmentation Proposals

- **Pattern 11 *Test-as-Spec and SPEC_DEVIATION Markers*** — augment with a sub-bullet noting that the same loop generalizes from functional tests to **architecture-rule tests**, citing ArchUnit as the canonical example: "Architecture-level invariants (layer access, dependency direction, naming, annotation presence) are testable with the same assertion-failure-as-feedback model. Tools like ArchUnit (Java) demonstrate the pattern; the abstraction transfers to any AST/IR layer." Cross-link from `topics/self-healing-and-verification.md` §4.

- **Pattern 11 — self-describing rule augment** — add a second sub-bullet: "Rules should be self-describing. ArchUnit's `DescribedPredicate`/`ArchCondition` carry their own English description, which the test runner embeds in the failure message alongside the violating file:line. The spec sentence appears in the feedback the agent receives. This is the inverse of the `SPEC_DEVIATION` marker (which annotates code with the deviation prose); both close the spec↔code↔feedback loop in opposite directions, and they compose."

- **Pattern 13 *Confidence Tagging on Inferred Data*** — extend the `EXTRACTED` discussion in `topics/patterns-worth-stealing.md` and `topics/self-healing-and-verification.md` §6 to note that ArchUnit reinforces the same principle at the *verifier* layer: rules are evaluated against bytecode (post-compile, deterministic) rather than source text. Suggested edit to the `EXTRACTED` definition: "ArchUnit's bytecode-graph approach is a second example: it sees what the compiler actually produced — accurate dependency edges, no false positives from comments, string literals, or string-template package names. The wider design principle: spec verifiers for AI-generated code should anchor on a post-compile/post-build artifact (AST, IR, bundle graph, bytecode) wherever possible, because AI agents are prone to 'looks-right' source output that fails the moment a deterministic substrate is consulted."

## 5. Contradictions

None identified. ArchUnit's posture is consistent with the dossier on every point checked: ride on existing test infra, prefer deterministic substrates, self-describe failures, treat existing-debt and new-debt asymmetrically. The `FreezingArchRule` ratchet is a generalization of Pattern 10's per-decision opt-out tags rather than a contradiction.

## 6. Items rejected (with rationale)

- **Slices acyclicity / `@AppModule` JPMS-like modularization (`respectTheirAllowedDependenciesDeclaredIn`).** The mechanism is Java-package-name-syntactic and assumes a JVM module system. The transferable abstraction (named architectural primitives, dependency-graph rules) is already captured in finding 8 above; reproducing the Java-specific surface adds noise without adding spec-driven-AI-framework signal.
- **`GeneralCodingRules` catalog (`NO_CLASSES_SHOULD_USE_JAVA_UTIL_LOGGING`, no field injection, no `System.out`).** A language-specific lint catalog. The transferable abstraction (importable rule packs) is captured in finding 7.
- **`ImportOption.DO_NOT_INCLUDE_TESTS` / `DO_NOT_INCLUDE_JARS` import filters.** Mechanical detail of bytecode loading; not a load-bearing spec-framework concept.
- **`ClassFileImporter` API surface and `JavaClass`/`JavaMethod` reflection-mirror domain model.** Implementation detail of how ArchUnit gets to a graph; the transferable insight (deterministic substrate over text) is captured in finding 6.
