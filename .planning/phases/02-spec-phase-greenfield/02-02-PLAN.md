    Always cover all five categories in this exact order: (1) Problem, (2) Who it's for, (3) Constraints, (4) Success Criteria, (5) Out-of-scope.
    For each category: open with a focused starting question. After each answer, evaluate: is it specific enough to write a concrete spec section? (Specific = names facts, conditions, or numbers. Vague = abstract generalities or "it depends.") If vague and fewer than 3 turns used in this category: ask one targeted follow-up probe. Advance to the next category when: (a) 3 turns are spent in this category, OR (b) the answer is specific enough — the agent decides, not the user (per D-02).
    Inline research trigger (per D-03b): at any point during Q&A, if the user says "research X" or asks to look something up, immediately execute Step 3 for that topic, then resume Q&A from where it left off.

    Two trigger modes — handle both identically once triggered:
    (a) User-requested: user says "research <topic>" at any point during Q&A — trigger immediately.
    (b) Agent-suggested: at the end of Q&A, if knowledge gaps were detected, present a numbered list of proposed research topics and ask the user to accept or skip each individually.
    For each accepted research topic: use the Task tool to spawn a generalPurpose sub-agent. The sub-agent prompt must include:
    — Topic: <the research topic>
    — Project context: <1-2 sentence summary of what the user is building, drawn from Q&A answers so far>
    — Output file: .planning/research/RESEARCH-<topic-slug>.md where topic-slug is the topic lowercased and hyphen-separated (e.g. "stripe-pricing-model")
    — File format: # Research: <topic>, then sections: ## Summary (2-3 sentence executive summary), ## Key Findings (bullets), ## Implications for Spec (how findings shape constraints or success criteria), ## Sources (URLs or descriptions)
    — Instruction: "Keep the file concise — the spec author will read this before writing the final spec."
    After each sub-agent completes: Read .planning/research/RESEARCH-<topic-slug>.md and note the key findings for incorporation into SPEC.md.
    Multiple research sub-tasks may run; each produces its own file. All are read before the spec is finalized.

    STEP 4 — SPEC.MD ASSEMBLY (per D-06, D-07, SPEC-02):
    Merge all Q&A answers and all research findings. Use the Write tool to create .planning/SPEC.md with this exact template structure:
    Front-matter block: three-line block delimited by --- markers, containing: status: draft, version: 1, date: <today's date in YYYY-MM-DD format>
    Document body: # Spec: <project name from Q&A>, then five sections in order: ## Problem, ## Who It's For, ## Constraints, ## Success Criteria, ## Out of Scope. Each section contains the concrete answers gathered in the Q&A, enriched with research findings where relevant.

    STEP 5 — APPROVAL GATE (per D-08, D-09, SPEC-04):
    Present the full contents of .planning/SPEC.md to the developer.
    Ask: "Approve this spec? Reply with: yes / edit / abort"

If already "status: approved" (idempotent case): skip the patch. Confirm: "Spec approved ✓ — run /plan-phase to begin planning." Remind: "The plan-phase will verify approval via python3 mise-en-place/tool-validate-spec/validate_spec.py before proceeding."
    On "edit": ask "Which section would you like to revise? (Problem / Who it's for / Constraints / Success Criteria / Out-of-scope)". Return to Q&A for that category. Re-assemble and re-present SPEC.md. Re-prompt approval.
    On "abort": leave status as draft. Confirm: "Spec saved as draft in .planning/SPEC.md — resume with /spec-phase." Exit.
